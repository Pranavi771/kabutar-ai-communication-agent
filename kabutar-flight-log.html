kabootar, n. — a pigeon; historically, a carrier of messages.

Purpose

One machine, three processes

Kabutar runs entirely on a single computer — but not in a single window. Three separate processes are live at once, and mixing them up is the most common source of confusion.

Process 01

Flask server

The brain. Handles HTTP and SSE. No visible UI of its own — just a Python process in a terminal.

Process 02

Your browser tab

The control panel. localhost:5000 — where you type the command and watch it run.

Process 03

Automated Chrome

The hands. A second, separate browser window, driven by Selenium, logged into WhatsApp Web.

These are not the same window. The tab you click in and the Chrome instance that actually sends the message are two different browser processes.
Component Map

Where everything lives

Routing and logic are deliberately split into two files.

├── server.py                  HTTP + SSE layer only
├── agent_core.py              all real logic lives here

└── static/

server.py routes requests and frames SSE events. agent_core.py decides everything else — compose the message, resolve the contact, drive the browser, send the mail.

Request Flow

One send, traced end to end

  1. script.js reads the form
    Renders your message as a chat bubble, then opens a Server-Sent Events connection — a GET request, since native EventSource only supports GET.
  2. server.py streams back a response
    The /api/send route returns a generator wrapped in a text/event-stream response. The connection stays open.
  3. extract_intent() — the one LLM call
    Groq turns your free text into structured JSON: a subject and a message.
  4. resolve_contact() — pure local lookup
    A dict lookup in contacts.json. No network call.
  5. send_whatsapp() or send_email()
    The actual send. Email is fast; WhatsApp automation runs 5–30 seconds.
  6. Events stream back
    Each stage emits status, then a terminal done or failed event, back to script.js.
One open connection. Multiple events over time. Not polling, not WebSockets.
WhatsApp Automation — Lifecycle

A browser session that never closes

The Chrome instance is a module-level singleton — one shared session for the server's whole lifetime, not one per message.

Dedicated profile

A separate Chrome user-data directory, so Selenium never collides with a window you already have open.

Stale-lock cleanup

Chrome's own lock files are cleared before every launch — the fix for the "crashed" error left by an unclean kill.

Visible, on purpose

Not headless. Built for a live demo, where the audience needs to actually see it work.

Fast-path login check

A 3-second probe covers "already logged in." Only a fresh session waits out the full QR scan window.

WhatsApp Automation — The Send

Seven steps to one sent message

  1. Normalize the number
    Strip the plus sign, spaces, and hyphens.
  2. Open WhatsApp's own deep link
    web.whatsapp.com/send?phone=... — this only opens the chat, it doesn't send anything by itself.
  3. Handle "Continue to Chat," if it appears
    Shown for numbers not already in your chat history. A short timeout here is expected, not an error.
  4. Wait for the compose box
    Located by CSS selector, up to 30 seconds.
  5. Type it in — line by line
    Shift+Enter between lines, since a plain Enter submits the message instead of breaking the line.
  6. Enter, to actually send
Nothing raises past this function's own boundary. Success or failure is just a string, prefixed with "Failed:" or not — the CLI and the web UI both key off the exact same contract.

What it does not decide
  • ✕ Which platform to use — that's the dropdown.
  • ✕ Who the recipient is — dropdown, resolved client-side.
  • ✕ Whether to send at all — no approval step.
  • ✕ Which tool to call — only one is offered.
Narrow, single-step, schema-constrained function calling — not agentic multi-step tool use.
Routing

Five routes, three events

MethodRoutePurpose
GET/Serves index.html
GET/api/contactsList contacts
POST/api/contactsUpsert a contact
DELETE/api/contacts/<name>Remove a contact
GET/api/sendThe SSE stream
event: status
data: {"text": "..."}

The event name — status, done, or failed — routes the client's UI, separate from EventSource's own onerror, which only fires on a dropped connection, never on a business-logic failure.

Frontend

No framework, on purpose

index.html

Plain structure

No templating. Every dynamic value is injected by script.js at runtime, via direct DOM manipulation.

style.css

Dark theme, tokenized

CSS custom properties throughout. A low-opacity pigeon watermark with pointer-events: none, so it never intercepts clicks.

script.js

One file

No build step, no imports, no framework. Loaded with a plain script tag at the end of the body.

Known Gaps

What isn't here yet

Named on purpose — the honest gaps matter as much as what's built.

No authentication, anywhere
Fine while bound to localhost. Becomes a real concern the moment this gets tunneled or deployed.
No message history
Contacts persist to disk. Sent messages don't — refresh the page and the transcript is gone.
No retry or backoff
A transient failure on either send path is surfaced once, not retried automatically.
Selenium selectors are fragile
Tied to WhatsApp Web's current, undocumented DOM. If it changes, sending starts timing out.
contacts.json has no write-locking
Not a practical issue at one-user, one-process scale — worth naming for completeness.
